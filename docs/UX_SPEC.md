# Clinical Co-Pilot — UX Specification

**Owner:** Product / Front-End Engineering (React panel, `agent-ui/`)
**Status:** Authoritative — changes to any locked decision require updating this document first
**Cross-reference:** `ARCHITECTURE.md`, `USERS.md`, `docs/AGENT_CONTRACT.md`

This document defines the user-facing behavior of the Clinical Co-Pilot panel. It is the contract between the front-end team and the agent-api team. The response envelope shape, claim taxonomy, and responsiveness strategy defined here are normative — they govern what the React panel renders and what `agent-api` must return.

---

## 1. Overview

The Clinical Co-Pilot panel is a sidebar React application loaded inside OpenEMR by the thin PHP module at `interface/modules/custom_modules/oe-module-clinical-copilot/`. It serves one physician persona — Dr. Sarah Chen, a rounding hospitalist — in one specific workflow: morning triage (6:50–7:10 AM), hallway queries between rooms (7:15–11:00 AM), and handoff generation (11:00–11:30 AM).

The panel communicates with `agent-api` over two endpoints:

- `POST /agent/query` — all conversational turns (triage, briefings, queries, medication safety, handoff)
- `POST /agent/triage_rationale` — click-to-expand triage rationale (direct call, not a conversational turn)

The panel never communicates with OpenEMR's PHP layer during rounding. All agent communication goes directly to `agent-api`. OpenEMR's PHP-FPM pool is not in the query path.

## 2. UI-Owned Behaviors (Locked Decisions)

These three behaviors are owned by the React panel. They are never generated by the LLM, never routed through the dispatcher, and never replaced by a dynamic agent response. Any implementation that deviates from these must update this section and `ARCHITECTURE.md §4.7` first.

### 2.1 Static Greeting on Session Open

The React panel renders a static, UI-authored greeting string on mount. The LLM is not called. No network request is made for the greeting.

The greeting text is authored in React source. It may include:

- Optional `${providerName}` interpolation (from the session context injected by the PHP module)
- Time-of-day variant: "Good morning" / "Good afternoon" / "Good evening" selected by a JavaScript `Date` check, not by the LLM

The greeting may be warm. Example of an acceptable static greeting:

> "Good morning, Dr. Chen. Ready for your morning routine? Your census will load in a moment."

Example of an unacceptable greeting (LLM-generated, dynamic, variable scope language):

> "Good morning! I've analyzed your census and see several concerning patients today — let me start by..." ← NEVER. Not static. Not authored.

**Rationale:** The greeting is a product and compliance decision about scope-setting. It must be consistent, predictable, and sub-100ms. LLM-generated greetings introduce variability in scope-setting language and add latency to the user's first impression of session availability. Time-of-day variants are a JavaScript clock check — they require no LLM call.

### 2.2 Synthetic Census Auto-Dispatch

Immediately after the greeting renders and the census list is confirmed (provider ID and patient IDs resolved from the PHP module session context), the React panel auto-dispatches a synthetic message to `POST /agent/query`:

```json
{
  "session_id": "<session_id>",
  "message": "__census_summary__"
}
```

This message is constructed and sent by the UI without physician input. Dr. Chen does not type anything. She presses "Go" (or "Confirm census") and the panel sends the message on her behalf.

The response to this auto-dispatch is the UC-1 triage list — the ranked census ordered by clinical urgency.

**Rationale:** USERS.md UC-1 requires the triage list to be delivered automatically on session open with no physician query. The dispatcher loop requires a message to trigger tool selection. The UI sends the first message. This is not a push notification — it is the programmatic first turn of the conversation, triggered by session initialization.

**FHIR pre-fetch timing:** Pre-fetch fires on React panel mount, in parallel with the greeting render — NOT on the "Go" press. By the time Dr. Chen presses "Go," the FHIR bundles for all census patients are already landing in Redis. The auto-dispatch triggers `get_census_summary`, which reads from Redis (warm cache) rather than making cold FHIR calls during the UC-1 15-second budget window.

### 2.3 Click-to-Expand Triage Rationale (Direct Call)

When the physician taps "why?" or the expand affordance on a triage entry in the sidebar, the React panel calls `POST /agent/triage_rationale` directly:

```json
{
  "patient_id": "<patient_id>",
  "session_id": "<session_id>"
}
```

This is NOT a conversational turn. It does NOT appear in the conversation history. It does NOT consume a dispatcher loop iteration. The `agent-api` invokes `get_triage_rationale` directly without passing through the dispatcher.

**Conversational form:** When the physician types "why is bed 7 first?" into the chat input, that query goes through `POST /agent/query` as a UC-3 conversational query. Both paths must produce equivalent rationale content for the same patient, but they use different invocation paths.

**Rationale:** Triage rationale is a deterministic lookup against the cached rules engine output. Routing it through the dispatcher would add an unnecessary tool-selection step for a known, bounded, latency-sensitive operation. The 2-second click-to-expand budget cannot be met through the dispatcher loop. The direct endpoint exists for exactly this case.

## 3. Session-Open Flow

The sequence from login to first response:

1. **OpenEMR login.** Dr. Chen authenticates to OpenEMR as normal. No separate agent login.
2. **PHP module loads.** `oe-module-clinical-copilot/index.php` reads the OpenEMR session context (provider ID, session date) and returns an HTML page loading `copilot.js`. No agent calls yet.
3. **React panel mounts.** `copilot.js` executes in the browser.
4. **Static greeting renders immediately.** Sub-100ms. Constant string with optional name/time-of-day interpolation. No LLM call. No network request.
5. **FHIR pre-fetch fires in parallel with greeting render.** The React panel signals `agent-api` to begin pre-fetching all 7 FHIR resource types for all census patients simultaneously. Pre-fetch populates Redis. This fires at mount — not on the "Go" press.
6. **Dr. Chen reviews the census list and presses "Go."** She may adjust the census (add/remove patients) before pressing Go.
7. **React auto-dispatches the synthetic census message** to `POST /agent/query`. This is the first conversational turn. Dr. Chen typed nothing.
8. **`agent-api` runs the dispatcher.** Dispatcher routes to `get_census_summary`. The tool reads FHIR bundles from Redis (pre-fetch already completed), runs the deterministic rules engine, and calls the LLM for one-line explanations only.
9. **UC-1 triage list streams back within 15 seconds.** First content visible to Dr. Chen.
10. **Session is active.** All subsequent queries use `POST /agent/query`. Conversation history accumulates. Census context block stays cached.

## 4. Response Type Ownership

Every `POST /agent/query` response returns the following typed envelope. The `type` field determines which React renderer handles the response.

```typescript
interface AgentResponse {
  type: "census" | "briefing" | "query_answer" | "medication_safety" | "handoff" | "text";
  data: CensusData | BriefingData | QueryAnswerData | MedicationSafetyData | HandoffData | null;
  narrative: string;        // physician-facing prose summary, always present
  citations: Citation[];    // may be empty for conversational/UX text responses
}

interface Citation {
  patient_id: string;
  resource_type: string;       // "Observation", "MedicationRequest", etc.
  resource_id: string;
  effective_datetime: string;  // ISO 8601
  value_summary: string;       // human-readable: "K+ 5.9 mEq/L"
}
```

**Type field descriptions:**

| Type | Produced by | React renderer | Clinical assertions require citations |
|---|---|---|---|
| `census` | `get_census_summary` | `CensusRenderer` | Yes — all flag values, lab values, vital readings |
| `briefing` | `get_patient_briefing` | `BriefingRenderer` | Yes — all clinical claims |
| `query_answer` | `query_patient_records` | `QueryAnswerRenderer` | Yes — sourced values; not-found responses cite search window |
| `medication_safety` | `get_medication_safety` | `MedicationSafetyRenderer` | Yes — allergy entries, lab values, condition names |
| `handoff` | `generate_handoff` | `HandoffRenderer` | Yes — open items, events, plan elements |
| `text` | Dispatcher fallback / clarification | `TextRenderer` | No — conversational/UX text only |

The `type` field is set by the tool that produced the response. The dispatcher does not downgrade the type except on error recovery, where it falls back to `"text"` with a safe message.

**`get_triage_rationale` (direct call):** Returns its own envelope with type `"rationale"` — not routed through the dispatcher response pipeline. Handled by the `PatientCard` expand affordance renderer.

## 5. Responsiveness Strategy

**Decision: token streaming via SSE (Server-Sent Events)**

The React panel implements token streaming for `POST /agent/query` responses. The `agent-api` returns a streaming SSE response; the React panel renders tokens as they arrive into the `narrative` field of the response envelope.

**Rationale:**

- UC-3 has a 3-second total budget. Streaming reduces perceived latency because the physician sees the first tokens of the answer within ~500ms of the tool returning, rather than waiting for the full response to be assembled and returned.
- The Anthropic SDK supports streaming natively via `client.messages.stream()`. No additional infrastructure is required.
- For UC-1 (triage list, 15-second budget) and UC-5 (handoff, 20-second budget), streaming provides progressive disclosure — Dr. Chen sees patients arriving as each one-line explanation completes rather than waiting for the full list.
- Streaming is compatible with the typed response envelope: the `type` and `data` fields are emitted first in a metadata SSE event; `narrative` tokens stream after; `citations` are emitted in a final SSE event when the tool result is finalized.

**Non-streaming fallback:** If the SSE connection fails or the client does not support streaming, the panel falls back to polling `POST /agent/query` with a timeout and renders the complete response when received. This is the degraded mode — tool-progress indicators (spinner with "Searching chart...") are shown during the polling wait. The fallback does not affect clinical correctness.

**`POST /agent/triage_rationale`** is not streamed — it is a direct call with a synchronous JSON response. The 2-second budget is met without streaming.

## 6. Claim Taxonomy

This taxonomy determines which response fields require FHIR citations and which do not. It governs the verification layer (source attribution check) and the citation rendering in the UI.

### 6.1 Clinical Assertions — Citations Required

A clinical assertion is any claim that presents a specific value, status, or finding from the patient's chart. These must cite the FHIR resource (type, resource ID, timestamp) that supports the claim.

**Examples of clinical assertions (citations required):**

- Lab values: "K+ 5.9 mEq/L (Observation/obs-abc, 2026-04-29 03:12)"
- Vital signs: "RR 26, HR 118 as of 06:30"
- Medication names and doses: "Lisinopril 10mg daily added overnight"
- Diagnoses and problem list entries: "Admit diagnosis: COPD exacerbation"
- Allergy entries: "Documented allergy: Penicillin — reaction: rash"
- Code status: "Code status: Full code (Observation/obs-xyz, 2026-04-28)"
- Isolation status: "Contact isolation — MRSA"
- Pending items with elapsed time: "Nephrology consult unanswered — 7 hours elapsed"
- Any quantitative value from the chart: creatinine, sodium, INR, hemoglobin, etc.

**The hard rules (verification layer enforces these regardless of LLM output):**

- If the allergy section has any blank fields: NEVER "no known allergies." ALWAYS "Allergy section incomplete — [N] of [M] fields blank — verify directly."
- If code status field is blank or absent: ALWAYS flag as "Code status: NOT DOCUMENTED — verify before rounds."
- If a critical value's observation timestamp is older than 30 minutes at time of delivery: ALWAYS flag with "Value as of [timestamp] — verify current value in chart."

### 6.2 Conversational and UX Text — No Citations Required

Conversational text is any phrase that describes the agent's behavior, acknowledges a question, or transitions between topics. These do not cite FHIR resources.

**Examples of conversational/UX text (no citations required):**

- Greetings: "Good morning, Dr. Chen." (also UI-owned, never LLM-generated)
- Transitions: "Here is the briefing for bed 512."
- Not-found acknowledgments: "I searched 24 months of encounters and 12 months of labs and found no echo results for this patient." (The search window statement is required; the not-found statement itself does not cite a FHIR resource)
- Clarification requests: "Did you mean the patient in bed 501 or bed 512?"
- Refusal language: "I can surface what the chart says about X. The clinical decision is yours."
- The mandatory disclaimer footer: "This summary is generated from EHR data as of [timestamp]. Verify critical values directly in the chart."

**The boundary:** A statement about absence of data does not require a FHIR citation, but it must explicitly state what was searched and the search window. "Nothing found" is never acceptable without specifying what and where.

## 7. Latency Budgets

| Use Case | Target | Measurement Point |
|---|---|---|
| UC-1 — Morning triage list | < 15 seconds | From auto-dispatch send to last patient line rendered |
| UC-2 — Patient briefing | < 5 seconds | From physician tap/query to complete response rendered |
| UC-3 — Targeted record query | < 3 seconds | From query send to first tokens visible (streaming) |
| UC-4 — Medication safety surface | < 5 seconds | From query send to complete response rendered |
| UC-5 — Handoff generation | < 20 seconds | From "Give me handoff" send to full census block rendered |
| Click-to-expand rationale | < 2 seconds | From expand tap to full rationale rendered |

These budgets are met under normal conditions (Redis warm, FHIR bundles pre-fetched). In degraded mode (Redis unavailable, cold FHIR fetch required), the panel displays a latency warning banner. See `ARCHITECTURE.md §3.4` for degraded mode behavior.

## 8. Refusals

The agent explicitly refuses the following requests. These refusals are implemented in the system prompt, enforced by the verification layer's domain constraint check, and must be handled gracefully in the UI.

**What the agent refuses:**
- Placing, modifying, or suggesting specific medication orders
- Making a diagnosis
- Recommending ICU transfer directly
- Discharging a patient or generating a discharge order
- Accessing records of patients not on the active census (without explicit cross-coverage confirmation)
- Answering questions about other physicians' patients without documented cross-coverage

**Standard refusal language (reproduced from USERS.md §6):**

> "I can surface what the chart says about X. The clinical decision is yours."

> "This patient meets 2 of 3 qSOFA criteria based on current vitals as of [time]. This warrants your assessment."

**Examples of correct vs. incorrect agent output:**

Correct: "Current vitals meet qSOFA criteria of 2/3 — see vitals documented at [time]."
Incorrect: "This patient has sepsis." — NEVER

Correct: "I can show you the documented allergy list and relevant labs. The prescribing decision is yours."
Incorrect: "You should avoid prescribing X because..." — NEVER a specific order recommendation

**Mandatory disclaimer footer** on every response:

> *This summary is generated from EHR data as of [timestamp]. Verify critical values directly in the chart.*

The UI renders this footer below every `narrative` field in every response type. It is not optional. It is not conditional on whether critical values are present.

## 9. Contradictions Found

No contradictions found between `ARCHITECTURE.md` and `USERS.md` on the reviewed topics:

- **Greeting ownership:** ARCHITECTURE.md §4.7 and the CLAUDE.md clinical co-pilot section both state the greeting is static, UI-authored, and must not be LLM-generated. USERS.md does not address greeting authorship, which is consistent (not contradictory).
- **Click-to-expand dispatch:** ARCHITECTURE.md §4.7 and §1.4 both specify `POST /agent/triage_rationale` as a direct call bypassing the dispatcher. USERS.md UC-1 describes "why is bed 7 first?" as a physician query — this is consistent with the conversational form going through the dispatcher, as documented in ARCHITECTURE.md §4.7's final paragraph.
- **Session-open synthetic message:** ARCHITECTURE.md §4.7 documents the auto-dispatch. USERS.md UC-1 states the triage list is "delivered: automatically generated on session open, no query required." These are consistent — the auto-dispatch is the mechanism that satisfies the no-query-required requirement.
- **Response type ownership:** ARCHITECTURE.md §4.6 defines the typed response envelope `{type, data, narrative, citations}`. USERS.md §5 defines per-use-case output formats. These are consistent; the envelope carries the structured output that satisfies each use case's output requirements.
